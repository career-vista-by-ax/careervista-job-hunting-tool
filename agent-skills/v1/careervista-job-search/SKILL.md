## Clickable questions, including setup

Before asking the first question, check the host's available tools for a native ask-user, structured-question or choice-picker interface. When available in the current mode, **call that tool** so choices are clickable; writing numbered options or Markdown checkboxes in chat is not a substitute. Use the host's equivalent rather than requiring a particular provider or tool name. Apply this to runtime/language choices, intake, search scope, follow-ups and document-editing choices.

Ask one question per call. Put the recommended choice first and label it, give a short reason, offer two or three useful choices and retain custom free text and an undecided path. Use the host's built-in custom-answer field instead of a duplicate Other option. Provide format guidance, not recommended amounts. Keep categorical decisions clickable. Wait for the user's submitted answer; a preselected choice, timeout or silence is not consent. With an asynchronous question, keep dependent work pending and continue only independent work.

If no suitable question UI is available in the current host/mode, briefly explain that limitation once, then offer concise numbered choices with custom input in chat. Do not claim text is clickable or build a separate website merely to ask questions. A rejected tool call is not proof that the UI is unavailable: check the tool error/schema and retry a corrected call first. File attachments use the host's attachment mechanism. Permission requests must use a surface allowed by the host's rules; an answer does not bypass execution approvals.

Read [references/setup.md](references/setup.md) to reuse a saved connection or guide first-time Docker/local setup. Ask one question at a time. Docker pull/start/update requires the user's permission for the concrete image, container, data volume and loopback port. A local download requires the user's chosen release/path. Keep existing work intact. Finish setup only after the exact returned localhost origin answers `/api/v1/agent-guide`.

Before the first intake question or any research, send a visible message with a clickable **Open CareerVista** link to that verified origin’s jobs page (`/`). Tell the user to click it to open the local page in their browser and see saved jobs as research progresses; a fresh workspace may be empty initially. This handoff is required for both new setup and reused connections. Use the actual verified host/port, never a guessed default or an API-guide URL. Share the page link again when the batch is handed over, and send the new link promptly if the app address changes. An automatic browser launch does not replace the message.

## Guided search

Read [intake.md](intake.md) for CV-first intake, privacy, location inference, regional sources, grounded progression and broad board-first search. Read it once per conversation; use it instead of fetching the duplicate `agent-intake` guide. GET `/api/v1/agent-guide`, `/api/v1/agent-guide/agent-workflow` and `/api/v1/agent-guide/language` from that origin. This packaged intake policy takes precedence over older app guidance about Australian-only scope, CV sanitisation, interview order or search-engine-first discovery. The running app remains authoritative for supported API fields and capabilities; no image update is required for this instruction change. After the privacy acknowledgement, read `agent-tasks` when available for compact task-level helpers over the same HTTP API; use the raw API when the installed version lacks them. Read `capture-interface` before saving listings and the selected source's guides (`seek`, `linkedin`, `collection` or `custom-sources`) before browsing. These HTTP guides make source collection available even when no separate capture skill is installed.

Keep each search economical. Read each required guide once per installed version in this conversation; fetch optional guides only for the operation being performed. After consent, use `agent-tasks` helpers by default when available: resume from `search-context`, retain the pinned profile once, then request `includeProfile:false` and `disposition:"pending"` for subsequent screening pages. Batch prepared operations with `--task batch`; preserve work order and inspect partial failures. Use raw HTTP only for unsupported operations or older versions. Keep large responses in local files and expose only selected previews, IDs, counts and errors to the model. Never dump a complete database, evidence batch, browser DOM or guide directory into the conversation.

Discover compact previews across the agreed families before detailed reading. Deduplicate and screen them in batches; capture and assess only selected candidates within the agreed detailed limit. When no batch size was specified, propose five detailed listings for the first pass and expand on request; preserve any limit already agreed. Reuse saved evidence and completed checkpoints; re-fetch only for a requested freshness check, changed advert or missing material evidence. Keep evidence quotes and explanations concise while retaining material qualifications, concerns and unknowns. Do not perform optional company research, CV tailoring or translations unless requested or required by the saved language preference. Stop at the agreed boundary and report uncovered queries; never silently weaken consent, evidence, coverage or budget rules. Treat host usage percentages as allowance indicators, not measured per-run token costs.

Search headless first: batch the agreed keyword/location variants on original job boards/employer sources and public APIs, with search engines supplementing coverage, then read selected original pages with headless HTTP or the Docker Playwright helper described in `collection`. Open the user’s default host browser only for an observed login/verification/access barrier or unavailable headless capability, stating the reason. Stop headless requests for a blocked source; keep accessible sources moving. Verify actual query/location and readable original content before saving evidence; snippets and suspicious responses remain unverified. This access order also applies when an older running app’s source guide says to open a browser immediately.

When host-browser fallback is needed, prefer supported accessibility/DOM text and targeted listing/link reads. Avoid full raw HTML and repeated whole-page snapshots. Use screenshots for layout, image-only content, incomplete text access or verification, following the host tool’s required inspection rules.

Explicit language instructions take priority, then the saved preference. The user's own prompt language is a signal when none is established; confirm only when ambiguous. Save the choice through the language API. Display names are English, 简体中文 and 繁体中文. Preserve source evidence and quotes in their original language; keep canonical assessment explanations in English and save bilingual explanations through the language guide.

Use the user’s custom goals, or begin the guided location-aware intake when none are supplied. Offer an optional sanitised Word/TXT CV with the intake guide’s pre-upload privacy recommendation before asking role questions; reuse authorised reviewed CV/profile context. Ask one consequential question at a time with a recommendation, choices, custom input and an undecided path. Reuse settled answers. Clarify missing responsibilities, related titles and realistic progression using CV evidence; resolve the target job market from reliable context and ask only when missing/ambiguous. Cover working arrangement, employment, local currency and compensation basis, equity, leave, benefits and review priorities as relevant. Propose regional sources with custom input and perform broad searches across approved title/skill families. Use the intake guide’s clickable choices when a requested level lacks supporting evidence; honour a confirmed stretch direction without inventing qualifications. Then agree sites, scope, listing limit and spending boundaries before researching and saving evidence-linked recommendations. Complete/checkpoint the run, verify saved records and send the user to the current jobs-table URL.

Existing data is preserved by default. For a fresh search with current jobs, offer continuing or archiving; read the `history` guide after the user's choice. Full reset is a separate two-confirmation action in Local data. Respect Recently deleted suppression and `job_in_trash` responses. Record only user-confirmed application facts. Application submission is a user-only handoff; this skill never submits or completes application forms. Outbound messages are outside this flow.

## When the user chooses to apply

Offer CV/cover-letter tailoring and a simulated 30-second reader review. Fetch the app's `ax-cv` and `ax-30-secs` guides, or use those standalone skills when available. Ask whether the user prefers manual edits in their own tool, a separate agent-created draft, or authorised editor control; honour an editing mode already chosen. Save distinct variants and exact copies used, then let the user record their own progress.

Recommend applying through the original advert on the website where this job was found and clicking that site's Apply button. Preserve job-board link-outs; never bypass them with extracted, redirected or guessed direct employer/ATS application links. A direct employer advert is valid only when the job was found there originally. Ask for the original advert if provenance is unclear. Preparing documents does not submit an application, send a message or mark the job applied.
