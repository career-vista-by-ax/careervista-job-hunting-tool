# Bounded research runs v1

`RunsService(app)` in `src/runs.ts` is the public boundary. Register `runsRoute` with the local server. All mutations have a stable operation identifier; identical retries preserve completed mutations, changed retries return 409. GET `/api/v1/runs` and `/api/v1/runs/:id` return persisted state, work checkpoints, counts, safe errors and budget provenance. A run pins an approved immutable profile revision and selected tracks; arbitrary professions and configurable source names are supported.

POST `/api/v1/runs` → `create({requestId,profileVersion,trackIds,sources,limit:25,budget:{amount,currency}})`. Sources are distinct user-selected IDs, such as `seek`, `linkedin` or a custom employer source. The run is ready for a separate compatible agent; starting it does not launch an agent or pretend to perform searches.

For each saved queue item use the following routes, all POST `/api/v1/runs/:id/`:

| Suffix | Service operation and JSON fields |
| --- | --- |
| `queue` | `enqueue(id,{operationId,workKey,trackId,source,url})` |
| `reservations` | `reserve(id,{operationId,workKey,estimate,currency})` |
| `authorize` | `authorize(id,{operationId,workKey,modelWork,reservationId?})` |
| `checkpoints` | `checkpoint(id,{operationId,workKey,status,jobId?,errorCode?})` |
| `costs` | `settle(id,{operationId,reservationId,actual:number|null})` |
| `control` | `control(id,{operationId,action,workKey?,sessionRef?,pageUrl?,userConfirmed?,amount?,currency?})` |

1. Queue only selected sources and approved track IDs. `workKey` is stable within a run. Returned work contains a stable `ingestionId` for evidence ingestion; use it for retries through the observation API, never write SQLite.
2. Before browser/model work, authorize the queued item. Declare `modelWork:false` for non-model collection. Every model operation first reserves a conservative estimate, then calls authorize with `modelWork:true` and the returned reservation ID. Each reservation authorizes one model operation. Inspect the returned state before performing external work.
3. Save evidence through the observation API before analysis, then checkpoint `collected` with its job ID. Later assessment needs another authorization (and reservation if it uses a model), then checkpoint `assessed` or `excluded`. Completed `assessed`, `excluded` and `duplicate` items stay complete. Checkpoint `failed` with optional partial saved job and a safe error code. A failed item may be authorized again. Identical retry IDs do not reapply completed changes.
4. Settle each reservation with actual cost in the run currency if the host exposes it, or null if unavailable. Never invent exact provider billing. Unknown actual cost keeps the conservative estimate committed to the budget; unused/rejected calls can settle at known zero. An unknown estimate cannot authorize model work. Costs use up to six decimal places; currencies are never silently converted.
5. `control` actions: `pause`, `stop`, `resume`, `cancel`, `complete`, `wait-signin`, `wait-verification`, `session-expired`, `set-budget`. Stop is resumable; cancellation and completion are terminal. Completing requires no pending/working items. Checkpoints from already authorized work may be saved while paused/stopped/waiting; the app retains partial evidence. Cancel before further work; externally saved evidence always remains in the app.
6. Before waiting for website access, the agent opens the source in its controlled browser. `wait-signin`/`wait-verification` record workKey, an opaque nonsecret sessionRef (letters/numbers/underscore/hyphen, at most 128), and pageUrl (query/fragment discarded). The user signs in directly there. Resume with the same sessionRef and `userConfirmed:true`. An expired session requires `wait-signin` with a new host session reference, user login, then matching resume. Store no passwords, cookies or session tokens. CareerVista does not promise persistence beyond the selected host's capability.

Suggested limit is 25 new jobs, configurable 1–500. Every newly linked saved job consumes one slot, including partial evidence on a failed item. Jobs already present when the run started and repeated links are duplicates and consume no new-job slots. An authorized uncaptured work item temporarily occupies one slot, preventing concurrent work from exceeding the limit. Duplicates/failed uncaptured work release that slot. Existing captured work may still be assessed at the collection limit. Queue cap is min(5000, limit×20); authorization cap is max(100,limit×10), bounding duplicate/failure loops. A capture that an external agent saved without first obtaining authorization can remain in the app even when the run refuses its limit-exceeding checkpoint.

Counters distinguish pending/working and cumulative captures/assessments, current excluded/duplicate/failed states, and unique new jobs. Counts overlap by stage; assessed/excluded jobs retain their capture count. They are not a partition. Work and reservations survive restart; `working` means interrupted/in-flight work needing inspection, not automatic replay. Use its same ingestionId to retry evidence safely. After a sign-in wait or restart the host resumes the same browser session if available and the same checkpoint.

Budget rejection persists `budget-exhausted` and an actionable safe error before any new model operation is authorized. Explicitly increase the cap with `set-budget` then resume, or resume and request a smaller estimate. Known cost above an estimate pauses future authorizations. The app gates its own work permissions and reservations; it cannot meter or limit unrelated agent-host token use or prevent a host from ignoring the interface. Provider fees, browser-host availability/platform/licensing and network access remain the chosen host's responsibility.

Safe error codes: `collection_failed`, `malformed_output`, `provider_failure`, `session_expired`, `unavailable`, `other`. Raw exceptions/provider output/credentials are not retained.

## Disposable storage and presentation

The agent creates and controls runs through the API after agreeing scope, sources, listing limit and spending cap in the conversation. Pause/resume/cancel and budget changes happen there. The webpage presents the saved jobs and reasoning, updating periodically while visible; it has no run-configuration forms. The agent never solicits website credentials and resumes access only after the user completes sign-in/verification in the same controlled browser.

`RunsService(app).storage()` returns `{directories,totalBytes,removedBytes,skippedSymlinks}`. Each directory entry contains `{kind,bytes,capBytes,maxAgeHours}`. `cleanupStorage()` returns the same report after cleanup and includes reclaimed bytes. HTTP: GET `/api/v1/runs/storage`; POST `/api/v1/runs/storage/cleanup` with `{}`. Only the dedicated `runs/` children of app-owned cache, temp and logs directories are inspected. The cap is 16 MiB each (48 MiB combined); temporary run files expire after 24 hours, run cache/log files after seven days. Cleanup removes expired files first and oldest files as needed to meet the cap, then empty directories. It runs at application startup and on explicit API request; run operations currently generate no accumulating filesystem logs or temp artifacts.

Cleanup skips symlinks entirely, including a symlink used as the dedicated runs directory. It never visits persistent evidence/database, profiles, credentials, supported browser sessions or global caches. Sessions survive ordinary cleanup; host session expiration is handled separately through the run checkpoint. Run records/reservations/operation receipts are persistent user data, not disposable cache. Backup/export/deletion must include `research_runs` and `run_operations` when those lifecycle operations are implemented.

Validation uses the approved application/HTTP seam and synthetic unrelated professions. It covers durable duplicate-free checkpoints, concurrent listing slots, retained partial failed captures, reservation-first budget accounting, unavailable actual cost, sign-in and verification waits, session expiration, stop/cancel, and stale/oversized interrupted-run files. Filesystem cleanup fixtures include a symlink to persistent session storage and verify its target is preserved. No live-source or actual provider-billing claim is inferred from these deterministic cases.

Lifecycle integration: `RunsService(app).forgetJob(jobId): void` is a savepoint-safe cleanup hook called before deleting a job, including inside deletion preview/transaction. It removes baseline/current job IDs and listing-specific queued URLs/keys/ingestion references, erases matching operation receipts, clears linked waits, and prevents replay of redacted work. The run pauses if still active. Anonymous historical capture/assessment counts and spending survive; `removedNewJobs` preserves historical limit consumption without retaining the removed job ID. This hook itself does not delete the job's evidence; the lifecycle transaction performs that deletion and may roll the whole operation back safely.
