Spec: Private agent-assisted job research and application tracking

## Problem Statement

Job hunting takes hours of repetitive searching, reading, comparing, and tracking. A single keyword search misses opportunities across related roles, while conventional trackers do not adequately represent personal working preferences such as decision authority, end-to-end ownership, visible impact, and avoidance of excessive approval layers or responsibility without authority.

The owner wants a private tool for an Australian job search across analytics engineering, data engineering, principal engineering, data leadership, and related tracks. The tool must reduce research effort without taking ownership of career decisions or applications. It must preserve evidence, explain uncertainty, and remain useful when job sites require human participation or cannot be collected reliably.

## Solution

Build an original, single-user, local-first research and application-tracking application. A local web interface and SQLite database hold the user's profile, preferences, source evidence, structured jobs, assessments, and application history. A separate browser-capable agent uses repeatable skills and a defined application interface to collect and analyse opportunities. The user handles login or human-verification steps and retains control over decisions.

The core loop is collect → assess → review → learn. Start with SEEK and LinkedIn discovery, follow employer listings, and selectively investigate shortlisted companies using sources such as Glassdoor where accessible. Support several approved search tracks in a bounded run. Save evidence before interpretation, preserve excluded opportunities, and show a sortable table with a job detail panel. Improve preferences from explicit feedback, with reversible changes and confirmation before new hard exclusions.

The first release prioritises research and tracking. Tailored documents and assisted applications are later work. Success means less time researching and more worthwhile opportunities identified, not more automated applications or a larger number of scraped pages. Establish a baseline and compare a real supervised session; no quantitative time-saving claim has yet been agreed.

## Implementation Decisions

- **Repository and ownership:** This is an original application in the private repository `career-vista-by-ax/careervista-job-hunting-tool`. The existing careervista workspace and any get-dre project are unrelated and must not be repurposed. Repository creation and specification publication do not authorise publishing the repository publicly.
- **Initial state:** This is a greenfield repository. There is no existing implementation, domain glossary, ADR, or test prior art to reuse. The terms below establish the initial vocabulary, not a claim about an existing schema.
- **Storage:** Use SQLite as the primary system of record. Prefer normal relational records and explicit migrations. DuckDB is not required for the initial transactional workflow.
- **Application boundary:** The local application owns validation, persistence, preferences, review decisions, and history. The separate agent uses a versioned public application interface rather than writing arbitrary SQL or directly modifying database files. TypeScript and Node.js are the selected application stack. The transport, agent host and frontend framework remain implementation choices to validate.
- **Conceptual modules:** Profile and preference management; search and collection runs; evidence ingestion and vacancy reconciliation; structured extraction and assessment; review and application tracking; backup/export/deletion. These are responsibility boundaries, not a requirement for separate services.
- **Vocabulary:** A Search Track represents an approved career direction. A Source identifies a discovery or enrichment origin. A Source Observation preserves content and capture context. A Job represents a vacancy and may link to multiple observations and tracks. An Assessment is an evidence-backed interpretation under a particular Preference Profile version. A Review Decision records the user's judgement. An Application Event records actual application progress. A Research Run tracks bounded work and resumable progress.
- **Public operations:** Read approved preferences and tracks; create or resume a run; submit source observations idempotently; request extraction and assessment; retrieve jobs with evidence and explanations; record explicit review decisions and application events; propose and accept preference revisions; export, back up, restore, and delete data. Invalid submissions must produce actionable errors without silently promoting incomplete output into trusted facts.
- **Evidence first:** Persist readable captured content, source identity, source URL, capture time, and collection context before invoking extraction. Retain meaningful revisions and previous assessments. Screenshots are supplementary when text does not preserve relevant evidence; full website mirroring is not required.
- **Repeatability:** Record the relevant evidence references, preference version, model identity where available, and analysis configuration/version. Reassessment creates traceable results rather than erasing the reasoning behind previous decisions. Repeatability means reproducible inputs and inspectable outcomes, not guaranteed identical probabilistic wording.
- **Reconciliation:** Link confident duplicates to one job while retaining source observations. Surface uncertain matches and source conflicts; do not silently merge ambiguous vacancies or discard contradictory evidence. Repeated ingestion of the same observation must not multiply jobs or events.
- **Search configuration:** Support shared and track-specific preferences, approved keyword variants, source selection, listing limits, and spending limits. The initial suggested batch is 25 new listings across selected tracks, adjustable by the user. Document how limits count duplicates and partially collected records; this detail is not yet settled.
- **Collection:** Start with SEEK and LinkedIn plus employer destinations. Prefer available reliable interfaces where appropriate, and use browser-assisted research where needed. Source support includes capability and failure reporting. Supervised discovery of a new website is an attempted workflow, not a universal scraping guarantee. Authentication and verification challenges pause work for the user.
- **Run integrity:** Save checkpoints and partial results, expose errors and counts, and allow safe resume. Distinguish collected, assessed, excluded, duplicate, and failed work. Enforce budgets before initiating further model work when the remaining allowance is insufficient; disclose uncertainty if a provider cannot supply exact cost information.
- **Filtering and relaxation:** Retain every collected candidate even when later excluded, including reason and applicable preference version. Diagnose access failure, narrow query terms, and actual preference conflicts separately. Ask before loosening requirements. Reassess saved records when relevant before recollecting.
- **Preference interpretation:** Model autonomy, end-to-end responsibility, access to decision-makers, visible impact, and approval layers as separate preferences. Do not use startup or corporate status as proof of culture. Keep collaboration, stakeholder negotiation, and people management distinct from undesirable organisational conditions.
- **Assessments:** Explain qualification fit, preference fit, practical constraints, and confidence separately. Labels such as strong, promising, and low fit need transparent rules; exact thresholds remain to be calibrated. Confirmed hard conflicts prevent a strong-fit label. Unknown information remains investigable and visible. An opaque percentage is insufficient.
- **Evidence quality:** Distinguish employer claims, contextual external reports, user-confirmed facts, and model inference. Keep observation dates and source context. Reviews and marketing language cannot establish a definitive workplace-culture verdict. Produce follow-up questions for material unknowns.
- **Compensation:** Preserve original figures and separately represent currency, period, base versus package, superannuation, and contract units when available. Keep external reports, model estimates, and personal adjustments separately attributed. Do not silently convert contract rates or packages using unstated assumptions. Missing salary is not an exclusion unless the user requires disclosure.
- **Feedback:** An individual review decision does not automatically become a general preference. Propose visible changes, retain versions, allow reversal, and confirm new hard exclusions. Opening a job alone must not silently change the profile.
- **Application history:** User decisions, agent recommendations, listing availability, and application status are separate dimensions. Append explicit history for application changes. Support association with existing application documents without requiring generation. Opening an application page is not submission.
- **Availability:** Record last successful verification and distinguish confirmed closure from inability to verify. Keep unavailable or expired jobs historically; omit confirmed closed jobs from the default active-opportunities view without overwriting application outcomes.
- **Interface:** Lead with a sortable table, saved filters, and a detail panel. Prioritise title, company, location/work arrangement, compensation with provenance, fit, concerns, freshness, and user status. Provide a small new-jobs/action-needed summary. Charts are secondary, not a first-release dependency.
- **Local operation and privacy:** Bind the initial app to the local machine and keep it single-user. Stored records remain reviewable without an agent or internet. Cloud analysis of public listings and resume experience is authorised, with resume contact details removed by default. Do not assume unrelated personal notes are authorised for cloud submission. Keep providers configurable and credentials outside normal exports.
- **Sharing and platforms:** Verify the complete Mac workflow first; design for portability but label Windows, Linux, and Chromebook support unverified until installation and browser-agent dependencies are tested. Friends use separate copies, databases, credentials, and model settings. Remote multi-user access is not part of this release.
- **Data lifecycle:** Backups must restore evidence, preferences, assessments, and application history together. Exports support CSV and JSON with documented scope. Explicit deletion removes targeted live records and associated data; explain that previously created backup/export files are separate copies and are not silently erased. Retention of rejected jobs is a default, not a restriction on user deletion.
- **Original implementation and provenance:** Learn from documented JobSync workflows rather than copying implementation. Maintain references and dependency-license records. No project license choice or future distribution permission is implied by this specification.

- **Distribution and runtime (owner clarification, 2026-10-18):** Build the frontend and local backend in TypeScript on Node.js. Use mise to manage the development/build Node environment. Select the latest stable non-prerelease Node.js and compatible stable packages when implementing/releasing, validate compatibility, then pin exact runtime/tool versions and dependencies for repeatability. Do not resolve floating latest versions on every user launch. Node 26.12.0 Current was the latest release verified on 2026-10-18; recheck at implementation. Reference: https://nodejs.org/en/blog/release/v26.12.0 and https://mise.jdx.dev/getting-started.
- **Self-contained release:** Provide a downloadable archive per supported OS/architecture containing compiled application assets, the tested Node runtime, required production dependencies/native libraries, and a launcher. A user must not need to install Node, mise, a package manager, compilers, Git or Docker separately. First local launch and review must work offline; cloud analysis and website collection inherently require network access. Docker may be an optional alternative, never the only path or a hidden prerequisite. Keep the local browser-based UI; do not add a bundled desktop shell/browser without a demonstrated requirement.
- **Installation lifecycle:** Provide one obvious install/launch flow per OS with small platform launchers over shared lifecycle logic, plus uninstall with an explicit keep-data or remove-data choice. Prefer a per-user, no-admin installation. Keep owned app/runtime/dependencies, persistent user data, and bounded disposable caches in distinct subdirectories of one documented installation root where possible. Record unavoidable external artifacts such as shortcuts, host skill registrations or credential-store entries in an ownership manifest. Uninstall removes only owned resources and never shared Node/mise installations, another project's files or the user's normal browser profile. Preserve data by default if the user does not choose deletion. Verify keep-data reinstall, complete owned-artifact removal and rollback/retry after failed installation.
- **No application account:** CareerVista is a local single-user application with no account registration, login screen or hosted authentication. Launching and reviewing saved jobs requires no sign-in. Model credentials are explicit optional configuration for cloud features, not an application account.
- **Website authentication:** The agent opens a job/research site using its browser-control capability. If authentication or human verification is required, it pauses and prompts the user to complete that step directly on the website, then resumes in the same controlled browser session. The application and agent must not request, capture or log website passwords. Maintain checkpoints, allow cancellation and handle expired sessions without losing saved work. Persist supported browser sessions separately from disposable caches; do not export session secrets in ordinary backups/exports or clear sessions merely to free cache space. Never promise cookie persistence beyond the selected agent host's capabilities.
- **Agent skills setup:** Include versioned skills/workflows in the release and register only owned entries with the selected browser-capable agent host. Prefer installation in the main flow; if host constraints require a secondary installer, make it explicit, guided and reversible. The app remains usable without the agent. The chosen host and any external dependencies must be disclosed and validated; do not claim the browser-agent capability is self-contained until the selected host's packaging and licensing permit it. Website login belongs exclusively to the user.
- **Disk discipline:** Avoid runtime package installation and unnecessary package/download caches. Set explicit size/age limits for app-owned caches and logs, clean temporary artifacts on success/failure and stale files after crashes, and show storage use with a clear-cache action. Keep persistent evidence, resumes, preferences, credentials and browser sessions outside disposable-cache deletion. Manage SQLite checkpoint/compaction safely rather than deleting live journal/WAL files. Repeated runs, upgrades and interrupted installs must not produce unbounded cache/temp growth. Do not automatically delete unrelated global caches.
- **End-of-work cleanup:** Use the owner's mac-deep-clean skill's dry-run-first, inspect-then-apply approach for scoped cleanup at the end of implementation. The locally available full script also targets DRE repositories, shared caches and Time Machine settings; those actions are outside this project's cleanup scope and must not be run indiscriminately. On other systems use equivalent app-owned cleanup. Report reclaimed space and retained data. The private machine-specific skill is a maintainer aid, not a required release dependency.

## Testing Decisions

- **Approved primary seam:** The user explicitly approved testing through the local application's public interface: submit captured listings and preferences, then verify saved evidence, explained assessments, review decisions, and application history. Prefer this single high-level seam over tests coupled to individual internal modules.
- **Test quality:** Assert externally observable outcomes, data integrity, and recoverability. Do not assert private function calls, incidental schema layout, exact generated prose, or a model's uncalibrated numeric score. Use deterministic browser/model responses in automated tests.
- **Coverage across modules:** Exercise profile versions, run orchestration, ingestion, reconciliation, assessment, review, application events, and backup/export through the same interface wherever practical.
- **Core acceptance journey:** Submit a captured listing under approved preferences; verify raw evidence is retained before analysis, structured details and supporting evidence are visible, the user can make a separate decision, and an application event persists across restart.
- **Idempotency and duplicates:** Submit the same observation repeatedly and resume interrupted work; verify no duplicate job/event creation. Submit confident cross-source duplicates, ambiguous matches, and conflicting compensation; verify preservation and appropriate review visibility.
- **Exclusion and reassessment:** Verify excluded jobs retain reasons, remain retrievable, and can reappear after a preference revision without recollection. Verify a recorded historical assessment still identifies the preferences and evidence that produced it.
- **Uncertainty and hard conflicts:** Unknown remote status or salary must not become an explicit mismatch. A confirmed hard conflict must not receive a strong-fit label. Conflicting or weak evidence must be exposed rather than converted into certainty.
- **Culture assessment:** Use curated cases including a startup with restricted authority and a larger organisation with explicit autonomy. Check evidence attribution and unsupported-claim avoidance, not agreement with a speculative culture verdict.
- **Salary semantics:** Exercise base versus total package, unknown superannuation treatment, different currencies, contract periods, external estimates, and user adjustments. Verify original values remain available and implied conversions are not invented.
- **Run resilience and budgets:** Exercise collection failures, verification pauses, model failures, malformed responses, interrupted runs, and exhausted budgets. Partial evidence remains usable, errors are visible, and safe resumption does not repeat completed mutations.
- **User control:** Verify applying a preference proposal is explicit and reversible, a dismissal does not automatically create a hard exclusion, and opening an apply URL never records a submitted application.
- **Availability:** Distinguish confirmed closure, successful active checks, and failed checks. None may erase application history.
- **Data lifecycle and privacy:** Round-trip a backup into an empty instance and compare user-visible records. Verify export scope, credential exclusion, deletion behaviour, and default contact-detail removal using synthetic data. Verify saved records remain reviewable offline.
- **Browser validation:** Run a supervised real-browser smoke test through at least one supported discovery source to ingestion and review. Before claiming initial source support, validate each advertised workflow. Live sites are unsuitable as the sole deterministic automated-test dependency.
- **Model validation:** Separately review a small representative evaluation set for useful explanations, grounded claims, handling of unknowns, and preference sensitivity. Record model/configuration context; do not claim deterministic test fixtures prove real-model judgement quality.
- **UI validation:** Use a small set of end-to-end checks for onboarding, filtering, detail review, feedback, and application updates. Verify essential keyboard operation and readable empty/error states. Avoid broad snapshot tests that merely mirror presentation implementation.
- **Prior art:** None exists in this new repository. TypeScript and Node.js are selected; the test framework and agent host remain to be chosen. Select them after validating the ingestion-to-review vertical slice.

- **Distribution acceptance:** Test self-contained launch and install/uninstall on supported Windows, Linux and macOS OS/architecture targets without preinstalled Node, mise, package managers or Docker. Check offline local launch, keep-data reinstall, complete owned-resource removal, failed-install recovery, and cache/log growth after repeated/interrupted runs. Browser-workflow support remains separately verified per host/platform. Check website login pause/resume and ensure passwords/session secrets never enter evidence or logs.

## Out of Scope

- Fully autonomous job hunting, unattended universal collection, challenge circumvention, or guaranteed access to every website.
- Automatic application submission, recruiter messaging, or acting on the user's behalf without explicit authorisation.
- Generated tailored resumes, cover letters, DOCX/PDF output, and assisted form filling in the first release. Existing documents may still be referenced in application history.
- Public hosting, public repository release, multi-user accounts, remote sharing of one installation, billing, or SaaS infrastructure.
- Fully offline model inference as a first-release requirement; local storage and offline review are required.
- Guaranteed culture predictions, verified salary estimates, invented achievements, or guarantees of indistinguishable-from-human writing.
- Simultaneous verified releases for every operating system and Chromebook environment.
- A large charting/analytics suite or a second analytical database without demonstrated need.
- Copying another project's implementation or treating private use as a substitute for license tracking.

## Further Notes

- This specification synthesises the owner's approved design discussion. It is the first-release umbrella specification; implementation issues can be sliced around observable outcomes without changing these acceptance expectations.
- The first implementation investigation should prove a narrow supervised vertical slice: one source observation → saved evidence → structured assessment → user review. Resolve the agent host, interface transport, and installation approach using that result before expanding collectors.
- JobSync is reference material: its documented discovery inbox, reviewable extraction, application history, and run transparency are useful patterns. Its documented score-based discarding conflicts with this product's explicit retention requirement and must not be reproduced.
