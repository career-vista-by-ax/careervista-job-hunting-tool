# Private backup and recovery

Open **Backup and restore** at the bottom of the local workspace. Download the private JSON backup. In a separate empty installation, choose the file (or paste the JSON), select **Restore backup**, then reload the workspace. The original installation remains independent. There is no overwrite mode: installations containing domain records reject restore. Keep the original data root and backup until recovery is verified.

Backups contain the entire relational domain database: evidence, jobs, approved profiles/tracks, assessments, review and application events, and any future additive domain tables. They do not copy the runtime, credentials directory, browser sessions, caches, logs or temporary files. Model providers must be configured again and source websites may require sign-in. Existing document references are preserved; external resume/letter files are not embedded, so copy those files separately if needed. Store backup copies privately: saved listing/profile text may itself include personal information. Restoring does not copy website passwords or tokens from the excluded secret storage, and does not sanitize user-supplied evidence text.

The local public operations are `new Backups(app).create()` and `.restore(backupObject)`. HTTP uses `GET /api/v1/backup` and `POST /api/v1/backup/restore` with JSON. The restore request accepts up to 128 MiB; normal API requests retain their 2 MB limit. Backup creation rejects larger snapshots with an actionable error rather than producing an unsupported recovery file. Failed restore leaves existing records unchanged.

Portable format version 1 includes format identity, creation time, trusted migration names, all domain table column names and rows, and SHA-256 checksum. The checksum detects accidental corruption; it is not a signature or encryption. Only backup files from trusted sources should be used. No SQL or filesystem path from the backup is executed. Unknown versions/migrations, altered checksums, malformed table shapes/value types/JSON columns, violated constraints and broken foreign-key relationships are rejected in an isolated in-memory validation database before destination mutation. Insertion into the empty destination is a single transaction with deferred relationship checks; any target incompatibility rolls back fully. Creation uses one SQLite read transaction, retaining a consistent snapshot even while another connection writes.

A backup from known older migrations can restore into a later additive schema: all its migrations must remain available in the destination, and known missing new tables remain at their empty defaults. Existing columns must remain compatible. Unknown future schemas require a compatible release. Do not edit applied migration files or remove older migrations. The format supports SQLite text, safe numeric and null values; binary domain columns require a future format encoding. Migration metadata and internal SQLite sequence tables are regenerated rather than copied. Restored explicit sequence values advance SQLite's sequence correctly.

Module contract: store credentials and browser sessions outside the domain database. Backups include every ordinary table except migration metadata; sensitive table names fail closed so new credentials/session tables cannot silently enter backups. Additive domain modules automatically participate and must extend public round-trip tests to compare their user-visible records. Every backup is private data, even though credential/session files are excluded.
