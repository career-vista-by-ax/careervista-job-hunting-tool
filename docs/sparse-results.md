# Diagnose sparse results before broadening

Diagnose results selects a saved Research Run and creates an immutable snapshot: successful and planned searches, observed access/collection failures, approved query variants, relevant saved jobs and actual hard-preference conflict reasons from assessments under that run's profile. An access failure is not zero results or proof that suitable jobs do not exist. Narrow/incomplete query coverage and evidenced preference conflicts remain separate facts. Run limits can intentionally stop coverage; the diagnosis does not override them.

`POST /api/v1/sparse-diagnoses` accepts `{operationId,runId}`. GET the collection or `/:id` for facts, prior reasons, saved jobs, recommendations and search proposals. Relevant jobs are identified from selected tracks, earlier assessments, run membership or approved terms in saved evidence. The module does not infer a culture/qualification conflict from silence.

Keyword changes use `POST /api/v1/search-proposals` `{submissionId,diagnosisId,trackId,keywords,explanation}`. They remain pending. POST `/:id/review` `{operationId,action:'accepted'|'rejected',confirmed:true}` explicitly accepts/rejects. Acceptance adds approved variants in a new profile revision without changing any hard/soft requirement. A stale active profile requires a fresh proposal.

Requirement changes use `POST /api/v1/sparse-diagnoses/:id/requirements` `{submissionId,trackId?,change:{key,kind,value},explanation}`. A saved evidenced conflict for that key/scope is required; failed collection alone cannot justify a requirement proposal. It creates an ordinary pending preference proposal linked to the diagnosis, with no fabricated user feedback events. Apply/reject/reverse through Preference proposals and the standard public action routes. Adding or restoring hard exclusions requires separate confirmation. Profile versions and source reasons remain available; no automatic weakening occurs.

`POST /api/v1/sparse-diagnoses/:id/reassess` accepts the reassessment batch contract, limited to relevant saved jobs/tracks identified by the diagnosis. Approve any revised profile first, then reassess from saved evidence before recollecting. Earlier exclusions remain in assessment history, and new reasoning explains which reasons changed. Review and application records remain independent.

The app offers controlled recommendations, not automatic resubmission or browsing. Private backups/exports retain diagnoses, proposals and histories. Deletion removes job-linked diagnosis rows and dependent requirement proposals rather than retaining orphaned evidence. Controlled public-interface tests separate failure-only, query-limited and genuine-conflict cases; verify rejected proposals preserve requirements; and exercise explicit acceptance, reversal and cached reassessment.
