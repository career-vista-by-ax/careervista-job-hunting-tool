# Search archives, recently deleted and application records

GET `/api/v1/archives` lists named search archives. POST `{operationId,name}` to archive every current, non-deleted job as one search. Their evidence, profile revisions, application events and copies remain intact. The current jobs view becomes empty, the active profile is cleared, and unfinished research runs are cancelled. Approve fresh goals before researching again. Language preference and reusable resumes are retained. The workspace `collection` filter selects `current` (default), `all`, `trash` or an archive ID; other filters still apply. Users can update archived applications and follow-up reminders.

GET `/api/v1/jobs/:id/storage` reads archive/deletion state. POST `{}` to `/storage/trash` moves the complete reconciled vacancy to Recently deleted; `/storage/restore` returns it to its previous search. Evidence and application records remain recoverable. Repeat captures with the same normalized source URL are rejected with `job_in_trash`; record the omission and respect the decision. Tracking parameters are ignored, but a different listing/cross-post is not assumed to be the same job without evidence. Review the trash via the workspace API before detailed capture where useful. Permanent deletion in Local data and full reset are separate explicit actions; they erase retained records and suppression history, so a future search can discover such listings again.

Application events support preparing, applied, screening, assessment, interview, offer, accepted, rejected, withdrawn and follow_up. The user can record progress directly in the job modal. These are local records, never application submissions. POST `/api/v1/jobs/:id/applications` with the existing event contract and optional `details`: stage, salaryAmount (original text), salaryCurrency, salaryBasis, salaryPeriod, noticePeriod, availableFrom, workRights, contacts (`name,role,email,phone,notes`) and questions (`question,answer`). Every update retains its own answer/contact snapshot. Record only user-confirmed facts. `followUpOn` is YYYY-MM-DD; 2/5/7/14-day shortcuts and custom dates set in-app due reminders, not email/system notifications. GET `/api/v1/applications/attention?on=YYYY-MM-DD` includes archived follow-ups, omits recently deleted jobs and terminal outcomes.

POST `/api/v1/jobs/:id/application-files` with `{operationId,name,kind,contentBase64}` stores an exact local copy. `kind` is resume, letter or other. Supported names end PDF/DOC/DOCX/TXT/RTF, up to 5 MiB each and 50 MiB total. GET that URL lists metadata; GET `/api/v1/application-files/:id` downloads the original bytes as an attachment. Reference the selected version in application-event `documents` as `{kind,label,reference:"application-file:FILE_ID"}`. Files, contacts, questions, archives and language settings are included in private backups and removed by full reset. Original source files stay outside the app.
